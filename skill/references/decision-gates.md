# 决策门与运行时选型

## 一、动手前先判定形态

大多数"专家团"是假团队：三四个 agent 各自包一层 LLM，里面其实是一次函数调用。按这棵决策树走，能降级就降级：

```text
流程完全确定、无判断点？（查工单、回写、渲染报告）
 ├─ 是 → 不是专家团，是 workflow。
 │       写 plan YAML 跑 exec-host runtime（token=0），或 fastlane workflow。
 │       平台上 squad 只当路由壳（用户 @ 的入口），成员可以是 0 个 LLM。
 ├─ 有判断点，但都在一个领域内？（诊断树遍历中提问、答案匹配）
 │    → 单专家 + 1 个 Skill，不建团。
 └─ 判断点跨 ≥2 个真正不同的领域，或链路里有必须的人工门禁？
      → 才建团。团长 = 确定性编排 + 极薄 LLM 措辞壳；
        每个成员按"单专家"标准独立成立，不成立就降级成脚本步骤。
```

示例判定：设备运维链（查询→诊断→预审→确认→执行→回写）里，真正的判断点只有"诊断树上的事实抽取/答案匹配"和"报告措辞"，终态就是一个用户入口 + 一张编排表 + 若干确定性 provider + 一处 LLM。

## 二、运行时三档

| 档 | 形态 | LLM 消耗 | 延迟 | 适用 |
|---|---|---|---|---|
| A. exec-host runtime | plan YAML + daemon 轮询 claim，squad 只是路由壳 | 编排 0 token；仅判断点一次 LLM | 秒级（实测 2~6s，重诊断 37s） | 链路基本确定的生产业务，默认档 |
| B. bridge 内联 | 团长单 task 内第一动作跑 `turn.py`，bounded slice 循环 | 1 个 LLM 会话 | 单轮内闭环 | 走平台 chat squad run、但要把整链收进一个 task |
| C. 平台原生 squad loop | SQUAD_OPERATING_PROTOCOL，LLM 团长 @mention 成员 | 每跳一个全量 LLM 会话 | 分钟级 | 只用于探索/演示，不用于承诺延迟的业务 |

配套规则：

- 模型分档：编排壳和路由用最便宜快的模型，只有判断点用强模型。
- 若 exec-host 线上不可用，选 B 档；不要退回 C 档做生产链路。

## 三、工程流程（把 v3 的规矩升格为标准）

1. **SDD 规格先行**：行为改动前先找 `docs/sdd/` 受影响规格编号；规格、追溯、实现、测试同批变更。
2. **影响分析前置**：跨角色/跨副作用的修改先填 change-impact 模板（状态、角色、issue 拓扑、artifact、外部副作用 + 并发/重复/旧事件检查）。
3. **发布即全层**：Skill 版本、Agent instructions、squad 绑定、发布包同批发，不得只动一层。
4. **验收看指标不看"已创建"**：新建 test 会话 + 版本核对 + 完整事件时间线 + 最终用户可见消息；调度次数/耗时/artifact 数/外部 API 调用次数任一异常不得宣布完成。旧会话、"子任务已创建"不算完成。
5. **runtime ledger 持续记**：生命周期/事件/续跑/版本绑定的观测按证据等级记入 ledger；平台缺口三层核对（业务仓库/backend/前端）后再动手。

## 四、存量专家团整改顺序

1. **先测量，不猜**：固定剧本跑一遍，按 ledger 格式记每跳耗时、token、dispatch 次数、artifact 数。
2. **逐团队过决策门**：能降级为"单专家+Skill"或纯 workflow 的立即降级。
3. **保留团的改造团长**：agents.md 按 `file-templates.md` 重写到 ≤120 行，第一动作接 turn.py（B 档）或 exec-host（A 档）。
4. **每个专家收敛到单 Skill 入口契约**，补契约测试与幂等键审计。
5. **验收**：延迟目标写进 acceptance-criteria（如查询 ≤60s、执行确认 ≤30s），CI + test 环境双门槛。
